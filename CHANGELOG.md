# Changelog

## [Unreleased]

* In-development version.

### Added

- **`ConstraintInterface::acceptedValueTypes(): list<ValueType>`, backed by the new `StrongType\Constraint\ValueType` enum and the `StrongType\Constraint\AnyValueType` trait.** Every constraint now declares the value types it can engage on, and every base type declares the one it holds as a typed `VALUE_TYPE` class constant (`Integer`→`Int`, `FloatingPoint`→`Float`, `StringType`→`String`, `BoolType`→`Bool`, `DateTime`→`String`, `ArrayType`→`Array`), inherited by every subclass. A custom constraint that is genuinely meaningful on every base can satisfy the new method in one line with `use AnyValueType;`.
- **`Nullable::unwrap(): (\JsonSerializable&\Stringable&HasEquals)|null`** returns the wrapped strong-type instance itself, where `getValue()` returns only its serialized primitive. This makes the wrapped object's own accessors reachable — `$nullable->unwrap()?->getValues()` on an array type, `->equals()`, `->__toString()` — without reconstructing it. The declared intersection type is the one `Nullable` already stores internally, so `jsonSerialize()`, `__toString()`, and `equals()` need no narrowing cast.

### Changed

- **A constraint attached to a value type it cannot engage on is now a definition-time error instead of a silent no-op.** Every constraint guards its own value type (`is_string()`, `is_int()`, ...) and returns "valid" for anything else. Because each base's value type is fixed, that fail-open default meant an inapplicable constraint could *never* fire: `#[Email]` on an `Integer` validated nothing, `#[Even]` / `#[Odd]` / `#[DivisibleBy]` no-op'd on float types, `#[Finite]` no-op'd on non-float types, an `AnyOf` with a non-engaging child short-circuited to satisfied and accepted **every** value, and a `Not` with a non-engaging child rejected **every** value. `ConstraintValidator` now checks each constraint's `acceptedValueTypes()` against the class's `VALUE_TYPE` when it first resolves the class — the same moment the constraint constructor invariants fire, i.e. the first construction of a value of that type — and throws `ConstraintConfigurationException` with a message naming the constraint, the class, and the accepted types (`"Positive is not applicable to String values on App\Score; it applies to [Int, Float]"`). This is a type-definition error, so it is a `\LogicException` and never a `StrongTypeException`, and it fires regardless of the value being constructed.
- **`InList` and `InEnum` derive an instance-specific applicability set from their arguments.** `InList` accepts the deduplicated value types of its allowed values, so `#[InList(1, 2)]` on a `StringType` — which under strict membership could never match a single value — is now a definition error rather than a type that rejects everything (`null` and object operands are ignored, and an allowed set of nothing else falls back to every type). `InEnum` accepts `[Int]` for an int-backed enum and `[String]` for a string-backed or pure one (a pure enum is compared against its case *names*), so `#[InEnum(SomeIntEnum::class)]` on a `StringType` is now a definition-time error instead of a constraint that silently never matches.
- **`AnyOf`, `AllOf`, and `Not` derive their applicability as the intersection of their children's.** Requiring every child to apply is what makes the vacuous-pass and dead-`Not` cases above detectable. An empty intersection — children with no value type in common, such as `AnyOf(new Min(0), new Pattern('/x/'))` — means the combinator can never engage on any single type and is a configuration error wherever it is attached.
- **The numeric constraints now guard `is_int() || is_float()` instead of `is_numeric()`.** `Min`, `Max`, `InRange`, `Positive`, `Negative`, `Nonnegative`, `Nonpositive`, and `Nonzero` previously engaged on numeric *strings* too, so `#[Positive]` on a `StringType` was only half-dead: it rejected `'-1'` but silently accepted every non-numeric string. That disagreed with the `[Int, Float]` set they now declare, and a declared set that does not match the runtime guard would let exactly that half-dead case back in. The guards now match the declaration. Behavior on `Integer` and `FloatingPoint` types is unchanged (`is_numeric()` and `is_int() || is_float()` agree on every `int` and `float`); a numeric-string type that leaned on this must state the rule with a string constraint such as `#[Pattern]`, or with a custom constraint.
- **`VALUE_TYPE` is declared `final` on all six bases.** A subclass that redeclared it could relabel its own value domain and reopen the fail-open hole (e.g. a `StringType` subclass claiming `ValueType::Int` to slip `#[Even]` past the check). `final` makes the base's value type non-negotiable for the whole hierarchy.
- **User-defined constraints must implement `acceptedValueTypes()`.** It is a required interface method rather than an opt-in capability, because a partial guarantee would leave exactly the holes this check closes. `use StrongType\Constraint\AnyValueType;` returns every value type in one line for a genuinely type-agnostic constraint; prefer an explicit set whenever `validate()` inspects a specific PHP type.
- **Exception hierarchy redesign: `StrongTypeException` now extends `\RuntimeException`, and a new `ConstraintConfigurationException` extends `\LogicException`.** Previously `StrongTypeException` extended `\LogicException`, which meant a genuine runtime validation failure (e.g. `new PositiveInt(-1)`) and a programmer's type-definition bug (e.g. `new DivisibleBy(0)`) shared the same base and could not be told apart by a `catch` block. `StrongTypeException` (and its subclasses `ConstraintViolationException`, `FormatException`) now root in `\RuntimeException`, matching the fact that every validation failure is triggered by caller-supplied runtime input. The new `StrongType\Exception\ConstraintConfigurationException` (`\LogicException`) is the single catchable category for type/constraint mis-definition: all constructor-invariant failures on `AllOf`, `AnyOf`, `DateFormat`, `DivisibleBy`, `ElementType`, `ExactCount`, `InEnum`, `InList`, `InRange`, `MaxCount`, `MaxLength`, `MinCount`, `MinLength`, `NotPattern`, and `Pattern` now throw it (previously bare `\LogicException`), as do `Nullable`'s type-wiring guards (non-strong-type or abstract `$type`). `catch (StrongTypeException)`/`catch (\RuntimeException)` and `catch (ConstraintConfigurationException)`/`catch (\LogicException)` are now cleanly separable in both directions — a `ConstraintConfigurationException` is never also a `StrongTypeException`.
- **`FixedSizeArray::tryFrom()` and `::nullable()` now throw `\BadMethodCallException` instead of `\LogicException`.** These factories are intentionally unavailable without a runtime `$size` — nothing is misconfigured, so they deliberately do not throw `ConstraintConfigurationException`. `\BadMethodCallException` still extends `\LogicException`, so existing `catch (\LogicException)` code keeps working.
- **The whole array hierarchy is now `readonly`.** `ArrayType::$values` was `public protected(set) array`, which let a subclass method reassign the validated array after construction without re-validating it — a `clear()` method could empty a `NonemptyArray` and leave it violating its own constraint. `$values` is now a plain `public readonly array`, and `ArrayType` plus all 15 concrete array types (`ListArray`, `AssociativeArray`, `NonemptyArray`, `EmptyArray`, `UniqueArray`, `FixedSizeArray`, and the nine `ArrayOf*` types) are declared `readonly class`. **Breaking for user subclasses:** PHP forbids a non-readonly class extending a readonly one, so an existing `class MyArray extends ArrayType` must become `readonly class MyArray extends ArrayType`. Immutability remains value-level, not element-level: object and resource elements are validated, not copied, and stay externally mutable by design — see [docs/semantics.md](docs/semantics.md#element-aliasing).
- **`Min` and `Max` render their bound with `var_export`, matching `InRange`.** A float bound was previously interpolated with PHP's default float-to-string conversion, so `UnitFloat`'s `#[Max(1.0)]` reported `"must be <= 1"` — reading as an integer bound. It now reports `"must be <= 1.0"`. Integer bounds are unchanged.
- **`FloatingPoint::__toString()` now renders through `json_encode`, so `(string) $float === json_encode($float)` always.** It previously used `strval()`, which applies the 14-digit `precision` ini and an upper-case exponent, while `jsonSerialize()` produces the shortest round-tripping representation with a lower-case exponent. The two disagreed on high-precision values (`1.2345678901234567` stringified as `"1.2345678901235"`) and on scientific notation (`"1.0E+20"` vs `"1.0e+20"`). Ordinary values are unaffected: `1.0` is still `"1"` and `-0.0` still `"-0"`.

### Fixed

- **Format-validating types now reject a trailing newline.** `DateString`, `TimeString`, `Rfc3339DateTimeString` (`Rfc3339`), `UuidString` (`Uuid`), and the `TimeFormat` constraint used `^...$` anchors, which in PHP allow a single trailing `\n` to satisfy the match (so `"2024-01-01\n"`, `"12:00:00\n"`, a UUID or RFC 3339 string with a trailing newline were accepted and stored verbatim). All are now anchored with `\A...\z`, matching the other format types, so a leading, trailing, or embedded newline correctly throws `StrongTypeException`.
- **`DateTimeString` (`DateTimeParseable`) now rejects surrounding whitespace, including Unicode whitespace.** `new \DateTimeImmutable()` tolerates leading/trailing whitespace — not just ASCII spaces, tabs, and newlines but Unicode separators like U+00A0 (no-break space) and U+202F (narrow no-break space) — so values like `DateTimeString("  2024-01-01  ")` or `DateTimeString("2024-01-01\u{00A0}")` were accepted and stored with the surrounding whitespace intact. The constraint now rejects any value with leading/trailing Unicode whitespace or control characters (`trim()` alone is ASCII-only and would miss the Unicode cases), so the stored value is always exactly the trimmed date/time string.
- **`DateFormat` is now deterministic for partial formats.** Validation prepends `!` to the parse format only, resetting fields absent from the format to the Unix epoch. Previously a partial format such as `m-d` inherited the *current* year, so `02-29` was accepted in a leap year and rejected otherwise — the predicate moved with the wall clock. It is now year-independent. `DateFormat` also rejects a format containing an unescaped `!` or `|` at construction (`ConstraintConfigurationException`): both are parse-only reset directives that `format()` echoes literally, so they can never round-trip. A backslash-escaped `\!` or `\|` is a literal character in both directions and is still accepted.
- **`ArrayType::equalsUnordered()` is now reflexive for arrays containing `NAN`.** The multiset match compared elements with `===`, and `NAN === NAN` is false, so `$a->equalsUnordered($a)` returned `false` for an array holding a `NAN` — while `equals()` returned `true` (PHP's array identity comparison short-circuits when both operands are the same array). The match now treats two `NAN` floats as the same element, the comparison `Unique` already uses for duplicate detection. Two distinct `NAN` values in the same multiset position therefore match; every other comparison remains strict. The allowance is top-level only (a `NAN` inside a nested element array is still compared strictly), and it is the only place the two methods differ in how they compare an *element* (they already differ by design on keys and order) — documented in [docs/semantics.md](docs/semantics.md#equality-semantics).
- **`Cidr` rejects a non-canonical prefix length.** `'10.0.0.0/08'` and `'0.0.0.0/00'` were accepted because the prefix was validated with `ctype_digit` plus an `(int)` cast, which silently ignores leading zeros. A leading zero is a second spelling of an in-range prefix length, so a single prefix length had several accepted forms. The prefix must now be canonical decimal — `0`, or a digit run with no leading zero. Every canonical spelling (`/0`, `/8`, `/24`, `/32`, `/128`) is unaffected. This canonicalizes the prefix length only: `Cidr` remains a format constraint, so the address half keeps the caller's spelling and host bits are still allowed.
- **`Nullable` no longer leaks raw PHP errors for a mis-wired type.** Pointing it at a class that implements `HasEquals` and `\JsonSerializable` but not `\Stringable` passed the type-wiring guard and then failed with a raw `\TypeError` when the instance was assigned to the intersection-typed internal property; the guard now checks `\Stringable` too and throws `ConstraintConfigurationException` up front, alongside the other wiring errors. A class whose constructor is not public was likewise accepted and then failed with a bare `\Error` on instantiation (and silently succeeded for a `null` value); it is now rejected up front as well. Pointing it at a type whose constructor *requires* more than one argument (`new Nullable(FixedSizeArray::class, [1, 2])`) raised a bare `\ArgumentCountError`; the constructor's arity is now checked by reflection alongside the other type-wiring guards, so it throws `ConstraintConfigurationException` naming the type — and, like those guards, it fires even when the value is `null`, where the old code silently built a `Nullable` that could never hold a value. Optional and variadic extra parameters do not count as required, so those types stay wrappable, and an `\ArgumentCountError` thrown from *inside* a valid one-argument constructor still propagates on its own terms rather than being relabelled.
- **Array-shape constraint failures can no longer fatal the process.** `IsList`, `IsAssociative`, and `IsEmpty` interpolated `print_r($value, true)` into their error messages. Because `print_r` invokes each element's `__debugInfo()`, an element whose `__debugInfo()` throws or returns a non-array turned a catchable validation failure into an uncatchable warning or a hard fatal (and the output was unbounded for large arrays). The messages are now bounded, element-safe summaries that report only the element count (e.g. "got a non-list array (2 element(s))"). Relatedly, `StrongType\Util\Stringify::value()` was rewritten to never call `print_r`: `true`/`false`/`null` render as those words (previously `1`/`''`/`''`), objects render as their type name (via `get_debug_type`), and arrays are walked element-wise with a small depth/element cap.
