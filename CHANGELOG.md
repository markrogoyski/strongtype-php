# Changelog

## [Unreleased]

* In-development version.

### Added

- **`ConstraintInterface::acceptedValueTypes(): list<ValueType>`, backed by the new `StrongType\Constraint\ValueType` enum and the `StrongType\Constraint\AnyValueType` trait.** Every constraint now declares the value types it can engage on, and every base type declares the one it holds as a typed `VALUE_TYPE` class constant (`Integer`→`Int`, `FloatingPoint`→`Float`, `StringType`→`String`, `BoolType`→`Bool`, `DateTime`→`String`, `ArrayType`→`Array`), inherited by every subclass. A custom constraint that is genuinely meaningful on every base can satisfy the new method in one line with `use AnyValueType;`.
- **`Nullable::unwrap(): (\JsonSerializable&\Stringable&HasEquals)|null`** returns the wrapped strong-type instance itself, where `getValue()` returns only its serialized primitive. This makes the wrapped object's own accessors reachable — `$nullable->unwrap()?->getValues()` on an array type, `->equals()`, `->__toString()` — without reconstructing it. The declared intersection type is the one `Nullable` already stores internally, so `jsonSerialize()`, `__toString()`, and `equals()` need no narrowing cast.

### Changed

- **A constraint attached to a value type it cannot engage on is now a definition-time error instead of a silent no-op.** Every constraint guards its own value type (`is_string()`, `is_int()`, ...) and returns "valid" for anything else. Because each base's value type is fixed, that fail-open default meant an inapplicable constraint could *never* fire: `#[Email]` on an `Integer` validated nothing, `#[Even]` / `#[Odd]` / `#[DivisibleBy]` no-op'd on float types, `#[Finite]` no-op'd on non-float types, an `AnyOf` with a non-engaging child short-circuited to satisfied and accepted **every** value, and a `Not` with a non-engaging child rejected **every** value. `ConstraintValidator` now checks each constraint's `acceptedValueTypes()` against the class's `VALUE_TYPE` when it first resolves the class — the same moment the constraint constructor invariants fire, i.e. the first construction of a value of that type — and throws `ConstraintConfigurationException` with a message naming the constraint, the class, and the accepted types (`"Positive is not applicable to String values on App\Score; it applies to [Int, Float]"`). This is a type-definition error, so it is a `\LogicException` and never a `StrongTypeException`, and it fires regardless of the value being constructed.
- **`InList` and `InEnum` derive an instance-specific applicability set from their arguments.** `InList` accepts the deduplicated value types of its allowed values, so `#[InList(1, 2)]` on a `StringType` — which under strict membership could never match a single value — is now a definition error rather than a type that rejects everything (`null` and object operands are ignored, and an allowed set of nothing else falls back to every type). `InEnum` accepts `[Int]` for an int-backed enum and `[String]` for a string-backed or pure one (a pure enum is compared against its case *names*), so `#[InEnum(SomeIntEnum::class)]` on a `StringType` is now a definition-time error instead of a constraint that silently never matches.
- **`AnyOf`, `AllOf`, and `Not` derive their applicability as the intersection of their children's.** Requiring every child to apply is what makes the vacuous-pass and dead-`Not` cases above detectable. An empty intersection — children with no value type in common, such as `AnyOf(new Min(0), new Pattern('/x/'))` — means the combinator can never engage on any single type and is a configuration error wherever it is attached.
- **The numeric constraints now guard `is_int() || is_float()` instead of `is_numeric()`.** `Min`, `Max`, `InRange`, `Positive`, `Negative`, `Nonnegative`, `Nonpositive`, and `Nonzero` previously engaged on numeric *strings* too, so `#[Positive]` on a `StringType` was only half-dead: it rejected `'-1'` but silently accepted every non-numeric string. That disagreed with the `[Int, Float]` set they now declare, and a declared set that does not match the runtime guard would let exactly that half-dead case back in. The guards now match the declaration. Behavior on `Integer` and `FloatingPoint` types is unchanged (`is_numeric()` and `is_int() || is_float()` agree on every `int` and `float`); a numeric-string type that leaned on this must state the rule with a string constraint such as `#[Pattern]`, or with a custom constraint.
- **`VALUE_TYPE` is declared `final` on all six bases.** A subclass that redeclared it could relabel its own value domain and reopen the fail-open hole (e.g. a `StringType` subclass claiming `ValueType::Int` to slip `#[Even]` past the check). `final` makes the base's value type non-negotiable for the whole hierarchy.
- **User-defined constraints must implement `acceptedValueTypes()`.** It is a required interface method rather than an opt-in capability, because a partial guarantee would leave exactly the holes this check closes. `use StrongType\Constraint\AnyValueType;` returns every value type in one line for a genuinely type-agnostic constraint; prefer an explicit set whenever `validate()` inspects a specific PHP type.
- **Exception hierarchy redesign: `StrongTypeException` now extends `\RuntimeException`, and a new `ConstraintConfigurationException` extends `\LogicException`.** Previously `StrongTypeException` extended `\LogicException`, which meant a genuine runtime validation failure (e.g. `new PositiveInt(-1)`) and a programmer's type-definition bug (e.g. `new DivisibleBy(0)`) shared the same base and could not be told apart by a `catch` block. `StrongTypeException` (and its subclasses `ConstraintViolationException`, `FormatException`) now root in `\RuntimeException`, matching the fact that every validation failure is triggered by caller-supplied runtime input. The new `StrongType\Exception\ConstraintConfigurationException` (`\LogicException`) is the single catchable category for type/constraint mis-definition: all constructor-invariant failures on `AllOf`, `AnyOf`, `DateFormat`, `DivisibleBy`, `ElementType`, `ExactCount`, `InEnum`, `InList`, `InRange`, `MaxCount`, `MaxLength`, `MinCount`, `MinLength`, `NotPattern`, and `Pattern` now throw it (previously bare `\LogicException`), as do `Nullable`'s type-wiring guards (non-strong-type or abstract `$type`). `catch (StrongTypeException)`/`catch (\RuntimeException)` and `catch (ConstraintConfigurationException)`/`catch (\LogicException)` are now cleanly separable in both directions — a `ConstraintConfigurationException` is never also a `StrongTypeException`.
- **`FixedSizeArray::tryFrom()` and `::nullable()` now throw `\BadMethodCallException` instead of `\LogicException`.** These factories are intentionally unavailable without a runtime `$size` — nothing is misconfigured, so they deliberately do not throw `ConstraintConfigurationException`. `\BadMethodCallException` still extends `\LogicException`, so existing `catch (\LogicException)` code keeps working.
- **The whole array hierarchy is now `readonly`.** `ArrayType::$values` was `public protected(set) array`, which let a subclass method reassign the validated array after construction without re-validating it — a `clear()` method could empty a `NonemptyArray` and leave it violating its own constraint. `$values` is now a plain `public readonly array`, and `ArrayType` plus all 15 concrete array types (`ListArray`, `AssociativeArray`, `NonemptyArray`, `EmptyArray`, `UniqueArray`, `FixedSizeArray`, and the nine `ArrayOf*` types) are declared `readonly class`. **Breaking for user subclasses:** PHP forbids a non-readonly class extending a readonly one, so an existing `class MyArray extends ArrayType` must become `readonly class MyArray extends ArrayType`. Immutability remains value-level, not element-level: object and resource elements are validated, not copied, and stay externally mutable by design — see [docs/semantics.md](docs/semantics.md#element-aliasing).
- **`Min` and `Max` render their bound with `var_export`, matching `InRange`.** A float bound was previously interpolated with PHP's default float-to-string conversion, so `UnitFloat`'s `#[Max(1.0)]` reported `"must be <= 1"` — reading as an integer bound. It now reports `"must be <= 1.0"`. Integer bounds are unchanged.
- **`FloatingPoint::__toString()` now renders through `json_encode`, so `(string) $float === json_encode($float)` always.** It previously used `strval()`, which applies the 14-digit `precision` ini and an upper-case exponent, while `jsonSerialize()` produces the shortest round-tripping representation with a lower-case exponent. The two disagreed on high-precision values (`1.2345678901234567` stringified as `"1.2345678901235"`) and on scientific notation (`"1.0E+20"` vs `"1.0e+20"`). Ordinary values are unaffected: `1.0` is still `"1"` and `-0.0` still `"-0"`.

### Fixed

- **Format-validating types now reject a trailing newline.** `DateString`, `TimeString`, `Rfc3339DateTimeString` (`Rfc3339`), `UuidString` (`Uuid`), and the `TimeFormat` constraint used `^...$` anchors, which in PHP allow a single trailing `\n` to satisfy the match (so `"2024-01-01\n"`, `"12:00:00\n"`, a UUID or RFC 3339 string with a trailing newline were accepted and stored verbatim). All are now anchored with `\A...\z`, matching the other format types, so a leading, trailing, or embedded newline correctly throws `StrongTypeException`.
- **`DateTimeString` (`DateTimeParseable`) now rejects surrounding whitespace, including Unicode whitespace.** `new \DateTimeImmutable()` tolerates leading/trailing whitespace — not just ASCII spaces, tabs, and newlines but Unicode separators like U+00A0 (no-break space) and U+202F (narrow no-break space) — so values like `DateTimeString("  2024-01-01  ")` or `DateTimeString("2024-01-01\u{00A0}")` were accepted and stored with the surrounding whitespace intact. The constraint now rejects any value with leading/trailing Unicode whitespace or control characters (`trim()` alone is ASCII-only and would miss the Unicode cases), so the stored value is always exactly the trimmed date/time string.
- **`DateFormat` is now deterministic for partial formats.** Validation prepends `!` to the parse format only, resetting fields absent from the format to the Unix epoch. Previously a partial format such as `m-d` inherited the *current* year, so `02-29` was accepted in a leap year and rejected otherwise — the predicate moved with the wall clock. It is now year-independent. `DateFormat` also rejects a format containing an unescaped `!` or `|` at construction (`ConstraintConfigurationException`): both are parse-only reset directives that `format()` echoes literally, so they can never round-trip. A backslash-escaped `\!` or `\|` is a literal character in both directions and is still accepted.
- **`ArrayType::equalsUnordered()` is now reflexive for arrays containing `NAN`.** The multiset match compared elements with `===`, and `NAN === NAN` is false, so `$a->equalsUnordered($a)` returned `false` for an array holding a `NAN` — while `equals()` returned `true` (PHP's array identity comparison short-circuits when both operands are the same array). The match now treats two `NAN` floats as the same element, the comparison `Unique` already uses for duplicate detection. Two distinct `NAN` values in the same multiset position therefore match; every other comparison remains strict. The allowance is top-level only (a `NAN` inside a nested element array is still compared strictly), and it is the only place the two methods differ in how they compare an *element* (they already differ by design on keys and order) — documented in [docs/semantics.md](docs/semantics.md#equality-semantics).
- **`Cidr` rejects a non-canonical prefix length.** `'10.0.0.0/08'` and `'0.0.0.0/00'` were accepted because the prefix was validated with `ctype_digit` plus an `(int)` cast, which silently ignores leading zeros. A leading zero is a second spelling of an in-range prefix length, so a single prefix length had several accepted forms. The prefix must now be canonical decimal — `0`, or a digit run with no leading zero. Every canonical spelling (`/0`, `/8`, `/24`, `/32`, `/128`) is unaffected. This canonicalizes the prefix length only: `Cidr` remains a format constraint, so the address half keeps the caller's spelling and host bits are still allowed.
- **`Nullable` no longer leaks raw PHP errors for a mis-wired type.** Pointing it at a class that implements `HasEquals` and `\JsonSerializable` but not `\Stringable` passed the type-wiring guard and then failed with a raw `\TypeError` when the instance was assigned to the intersection-typed internal property; the guard now checks `\Stringable` too and throws `ConstraintConfigurationException` up front, alongside the other wiring errors. A class whose constructor is not public was likewise accepted and then failed with a bare `\Error` on instantiation (and silently succeeded for a `null` value); it is now rejected up front as well. Pointing it at a type whose constructor *requires* more than one argument (`new Nullable(FixedSizeArray::class, [1, 2])`) raised a bare `\ArgumentCountError`; the constructor's arity is now checked by reflection alongside the other type-wiring guards, so it throws `ConstraintConfigurationException` naming the type — and, like those guards, it fires even when the value is `null`, where the old code silently built a `Nullable` that could never hold a value. Optional and variadic extra parameters do not count as required, so those types stay wrappable, and an `\ArgumentCountError` thrown from *inside* a valid one-argument constructor still propagates on its own terms rather than being relabelled.
- **Array-shape constraint failures can no longer fatal the process.** `IsList`, `IsAssociative`, and `IsEmpty` interpolated `print_r($value, true)` into their error messages. Because `print_r` invokes each element's `__debugInfo()`, an element whose `__debugInfo()` throws or returns a non-array turned a catchable validation failure into an uncatchable warning or a hard fatal (and the output was unbounded for large arrays). The messages are now bounded, element-safe summaries that report only the element count (e.g. "got a non-list array (2 element(s))"). Relatedly, `StrongType\Util\Stringify::value()` was rewritten to never call `print_r`: `true`/`false`/`null` render as those words (previously `1`/`''`/`''`), objects render as their type name (via `get_debug_type`), and arrays are walked element-wise with a small depth/element cap.
- **`NotPattern` no longer fails open when its regex cannot be evaluated.** `preg_match()` returns `false` (not `0`) on a regex engine error — backtrack-limit exhaustion, or a `/u` pattern against malformed UTF-8 — and `false` is falsy, so `if (preg_match(...))` treated an engine error identically to "no match" and let the value through. `NotPattern::validate()` now checks for `false` explicitly and rejects the value with `"{ShortClassName} type must be evaluable against pattern {pattern} (regex engine error), got {value}"`. `Pattern` was already safe here: its inverted guard (`!preg_match(...)`) already fails closed for the same `false` return.
- **Native `serialize()`/`unserialize()` can no longer bypass constraint validation.** PHP's default object deserialization writes straight into (even readonly) properties, skipping the constructor and `ConstraintValidator` entirely — a crafted payload could produce e.g. `PositiveInt(-5)`, and an ordinary `serialize()`/`unserialize()` round trip of an `ArrayOfResources` silently replaced its resource element with `int(0)` (PHP cannot serialize resources). Every base type, `FixedSizeArray`, and `Nullable` now implement `__serialize()`/`__unserialize()`, re-validating on the way back in — see the new Serialization section in `CLAUDE.md` for how. **Subclasses with constructor state beyond the base's must now also override `__serialize()`/`__unserialize()`**, the same existing obligation `tryFrom()`/`nullable()` already impose on a divergent constructor (see `FixedSizeArray`). **This changes the wire format**, `Nullable`'s especially (it now serializes the wrapped object itself rather than PHP's default private-property encoding): a value serialized before this change cannot be unserialized after it. The library is unreleased, so no compatibility shim is provided.
- **A subclass with unhandled extra constructor state can no longer silently corrupt its own serialization.** The obligation above ("subclasses with constructor state beyond the base's must override `__serialize()`/`__unserialize()`") was previously enforced only by documentation — a subclass that added a property (promoted or not) and forgot the override would either silently lose it on a round trip (an optional extra property) or crash `__unserialize()` with `\ArgumentCountError` (a required one), and only the first time someone actually serialized an affected instance. Every base's `__serialize()` now calls a shared guard (`StrongType\Util\SerializationStateGuard`) that reflects on every class in the runtime hierarchy — not just the runtime class itself, since `ReflectionClass::getProperties()` silently omits a *private* property declared by an intermediate ancestor when reflected from a more distant descendant — and throws `ConstraintConfigurationException` up front if any property exists beyond what that base's own `__serialize()` captures. The check matches each property against the known set by its actual declaring class, not by name alone, so a subclass that redeclares its own same-named private property (a distinct storage slot from the ancestor's, via PHP's private-property shadowing) is still correctly caught rather than mistaken for the base's own state. **A subclass can diverge the same way without declaring any extra property at all**, by overriding the constructor to *transform* its single argument instead of only validating it (e.g. `parent::__construct($value * 100)`) — inherited `__unserialize()` would feed the already-transformed stored value back through that same constructor a second time, silently reconstructing a different value than the one serialized. `SerializationStateGuard::assertConstructorIsSafeToInherit()` closes this separately: any constructor override below the base's own declaring class is untrusted by default and rejected, unless the subclass either writes a full `__serialize()`/`__unserialize()` override itself, or certifies — by overriding the new protected static `constructorPreservesSerializedStateVerbatim()` to return `true` — that the override stores its argument unchanged. `FutureTimestamp`, `PastTimestamp`, `Timestamp`, `DateString`, `TimeString`, `EmptyString`, `TrueValue`, and `FalseValue` all certify this way. The check is purely structural (it never invokes the constructor), so a validation-only override that legitimately depends on external state — `FutureTimestamp`/`PastTimestamp` comparing against `time()` — cannot have ordinary time drift misreported as a configuration error. A constructor requiring more arguments than inherited `__unserialize()` supplies is rejected unconditionally, regardless of certification. **The certification is bound to the specific class that declares the constructor it describes, not inherited transitively**: comparing only the returned boolean would let a further override — e.g. `ScaledTimestamp extends Timestamp` calling `parent::__construct($value * 100)` — silently inherit `Timestamp`'s "I only validate" certification for a constructor `Timestamp`'s author never saw and that does exactly the transforming thing the certification exists to rule out. `assertConstructorIsSafeToInherit()` now additionally requires the constructor's declaring class and the certification method's declaring class to match. **It also now rejects a `private` constructor outright, regardless of certification**: inherited `__unserialize()` calls `$this->__construct(...)` from the base's own scope (e.g. `Integer`), and PHP's `protected` visibility permits that call because the calling scope is an ancestor of the declaring class — but `private` is scoped to the exact declaring class only, so a subclass gating construction behind a `private` constructor plus a public static factory could previously pass arity and certification checks cleanly (including a truthful verbatim-storage certification) and still fail at deserialization time with `Error: Call to private method ...::__construct() from scope ...`, the first time a serialized instance was actually unserialized rather than the moment it was serialized.
- **A `Nullable` subclass can no longer inherit `Nullable`'s own `__serialize()`/`__unserialize()` and have its own invariants silently bypassed.** Unlike the six value-type bases, whose inherited `__unserialize()` re-runs a subclass's own validation by calling `$this->__construct(...)` again, `Nullable::__unserialize()` never invokes the constructor at all (see below), so a subclass's own constructor validation (e.g. forbidding a `null` value) or extra properties were never re-checked or re-carried — a crafted payload naming the subclass directly could produce an instance the subclass's own constructor would have refused. There is no reflection-based certification that can make this safe the way `constructorPreservesSerializedStateVerbatim()` does for the six bases, so `Nullable::__serialize()` and `__unserialize()` now both reject (`ConstraintConfigurationException`) whenever the specific method being called is still `Nullable`'s own, checked via `(new \ReflectionMethod($this, $method))->getDeclaringClass()` rather than a `static::class !== self::class` identity check (late static binding keeps `static::class` pointed at the subclass even *inside* a call it routed here itself via `parent::__serialize()`/`parent::__unserialize()`, so an identity check would incorrectly reject that pattern too). Every `Nullable` subclass must override both hooks itself — a trivial override that delegates to `parent::__serialize()`/`parent::__unserialize()` and then re-runs its own validation is the supported pattern. That trust in a delegating override is bounded to what it could have known about: a further-derived grandchild that adds its own property, *or* its own constructor validation with no new property at all (e.g. forbidding null), without also writing its own override, is still caught — the same gap `SerializationStateGuard` closes for the six bases. A `Nullable` subclass that also implements the legacy `\Serializable` interface is rejected outright, for the same reason a wrapped type implementing it is (see above) — though unlike that case, this can only fail fast on an ordinary `serialize()` call, not intercept a hand-crafted payload that bypasses `__unserialize()` via `\Serializable`'s own format sigil.
- **`Nullable` now requires the wrapped type to be safely serializable in its own right.** `Nullable::__serialize()` nests the wrapped object itself (to stay lossless — see below), but that is only safe to trust back if the wrapped object's own class is guaranteed to revalidate itself when reconstructed. A wrapped type without its own `__serialize()`/`__unserialize()` gets its properties written straight in by PHP's default object unserialization, with no constructor call at all — the same bypass this whole mechanism exists to close, one level down: a crafted payload could pair a valid `type` string with a wrapped object whose value was tampered directly, and `Nullable` had no way to detect it. Declaring the modern hooks isn't sufficient on its own either: a wrapped class that *also* implements the legacy `\Serializable` interface can still be exploited, since a serialized payload's own format sigil (`O:` vs `C:`) — not which methods the class declares — decides which reconstruction path native `unserialize()` takes, so a hand-crafted `C:`-sigil payload selects the unsafe legacy path regardless of a safe `__unserialize()` sitting right next to it. `Nullable::__serialize()` and `__unserialize()` now both require (`ConstraintConfigurationException` otherwise) that the wrapped class implements its own `__serialize()`/`__unserialize()` *and* does not implement `\Serializable`. A custom wrapped type without that guarantee remains fully usable through `Nullable` for construction, `equals()`, and JSON; it just cannot be serialized.
- **`equals()` and `equalsUnordered()` no longer crash on a self-referential array.** Comparing two distinct arrays that both contain a cycle back to themselves (`$a['self'] = &$a;`) with native `===` throws `Error: Nesting level too deep` — such arrays are otherwise valid, explicitly-supported `ArrayType` values (the `__toString()` fallback renderer already handles them, see `docs/semantics.md`). `StrongType\Util\ValueEquality` now catches that `Error` and reports `false`. There is no safe way to determine whether two such structures are "really" equal without risking the same unbounded recursion the crash comes from, so this never reports a false claim of equality — it only ever avoids the crash, in exchange for reporting "not equal" for two structures that (by construction) can never be proven identical. **`Unique` catches the same `Error` but rejects the value instead of reporting "not equal".** As a gatekeeper rather than an informational comparison, silently treating an unprovable pair as "not duplicates" would let a genuinely duplicated circular structure pass undetected — `Unique` now fails the value when a pairwise comparison it needs is indeterminate.
- **`Pattern`, `NotPattern`, and `Unique` now throw `ConstraintEvaluationException` (new) instead of returning an ordinary violation for an indeterminate value, so `#[Not(...)]` can no longer invert "couldn't be evaluated" into an accept.** `Not` only ever interprets its child constraint's *return value* as pass/fail; a returned violation string looks identical whether the value was confirmed invalid or simply couldn't be checked. Previously, a `#[Not(new Pattern('/.../u'))]`/`#[Not(new NotPattern('/.../u'))]` on malformed UTF-8 (a regex engine error) or a `#[Not(new Unique)]` on two indeterminate cyclic-array elements would have their "couldn't tell" result read as "the child failed" and inverted into a silent accept. `ConstraintEvaluationException` is thrown directly from `validate()` instead, and — since `Not` never catches exceptions from its child, only interprets its return — propagates uncaught straight through `Not`, the same way `ConstraintConfigurationException` already does (see the next entry for `AnyOf`/`AllOf`, which — having more than one child — specifically catch and retain it instead, so it does not always propagate all the way out of the constraint system for them). Direct (non-`Not`) use of `Pattern`/`NotPattern`/`Unique` is unaffected: the new exception extends `StrongTypeException`, so existing `catch (StrongTypeException)` code keeps working.
- **`AnyOf` and `AllOf` no longer let a child's `ConstraintEvaluationException` decide the outcome by order.** With more than one child, letting the first thrown exception abort evaluation immediately made the result depend on which child happened to run first: `AnyOf(NotPattern('/x/u'), MinLength(1))` rejected a malformed one-byte string, while `AnyOf(MinLength(1), NotPattern('/x/u'))` — the same two constraints, reversed — accepted it, since `MinLength` ran (and passed) first and the combinator never reached the throwing child. Both combinators now specifically catch `ConstraintEvaluationException` from each child (nothing else) and keep evaluating the rest: `AnyOf` accepts as soon as any child passes and re-throws the retained exception only if none does (a confirmed failure elsewhere doesn't help — the indeterminate child might have passed); `AllOf` returns as soon as any child reports a confirmed violation (preferred over reporting an indeterminate one) and re-throws the retained exception only if every other child passes. The result no longer depends on argument order.
- **`Min`, `Max`, and `InRange` reject a `NAN` bound.** Every comparison against `NAN` is false, so `#[Min(NAN)]`, `#[Max(NAN)]`, and `#[InRange(NAN, NAN)]` previously accepted every finite value instead of ever engaging — the same fail-open shape the value-type applicability check exists to close, just via a bad constructor argument rather than a misapplied attribute. All three now throw `ConstraintConfigurationException` at construction when given a `NAN` bound.
- **`DateFormat` no longer leaks a raw `\ValueError` for an embedded NUL byte.** `\DateTimeImmutable::createFromFormat()` throws `\ValueError` — not its usual `false` return — when the subject string contains a NUL byte. `DateFormat::validate()` now catches it and reports the normal constraint-violation message instead of letting the engine exception propagate past the constraint system.
- **`Nullable::equals()` is now exact-class, and the wrapped type name is canonicalized once at construction.** `equals()` previously used `instanceof self`, which also matched a subclass instance of `Nullable` itself, and compared the wrapped-type class-string field verbatim, so `PositiveInt::class` and `'\StrongType\Int\PositiveInt'` — the same runtime class — compared unequal. `equals()` now checks `$other::class` exactly. The type string itself is canonicalized (via `ReflectionClass::getName()`) once, at construction and at `__unserialize()`, rather than at each comparison site — every stored `$type` is always the true declared class name, so `equals()` and the wrapped-value class check both compare it directly with no further normalization needed.
- **`ArrayType::__toString()`'s fallback renderer can no longer exhaust memory on a self-referential array with more than one cycle back to itself, or on a wide array sitting past the depth guard.** The existing depth guard (`STRINGIFY_MAX_DEPTH`) only bounds the length of a single recursive path; an array with several independent self-references at the same level (e.g. `$a['x'] = &$a; $a['y'] = &$a;`) branches at every level instead, producing exponentially many nodes well within that depth bound and exhausting memory before any single path hit the cap. A total-node budget (`STRINGIFY_MAX_NODES`, 10,000) is now threaded through the renderer alongside the depth guard, bounding total work regardless of branching shape; a node that exhausts the budget renders as `"*TRUNCATED*"`, distinct from the existing depth-exhaustion `"*RECURSION*"` marker — see [docs/semantics.md](docs/semantics.md#string-representation-of-non-json-encodable-arrays). The budget and depth checks were initially ordered depth-first, so a node past the depth guard returned its `"*RECURSION*"` marker without ever decrementing the budget — a wide array sitting at that boundary (e.g. 100 branches of 20,000 elements each) was therefore still fully iterated, one budget-free `"*RECURSION*"` per leaf, reproducing the same exhaustion the budget exists to prevent. The budget is now checked and decremented first, so every node visited — regardless of depth — counts against it.
- **`Base64` no longer fails open under `#[Not(new Base64)]` for a large, valid, canonical base64 string.** Its regex prefilter could hit PCRE's JIT stack limit on inputs around 1 MiB, making `preg_match()` return `false` (an engine error) rather than `0` (no match); the code treated the two identically as an ordinary violation, so `Not(Base64)` inverted "couldn't be evaluated" into an incorrect accept — precisely the fail-open shape `Pattern`/`NotPattern` already guard against for the same underlying PCRE behavior. The regex prefilter is removed entirely: validation now relies solely on `base64_decode($value, true)` plus a re-encode round-trip check, which was already required to catch non-canonical encodings and needs no PCRE evaluation at all, so the failure mode cannot recur.
- **`DateFormat` validation no longer depends on the process's default timezone.** A purely calendar format like `Y-m-d` was parsed against whatever `date_default_timezone_set()` happened to be configured, and for a handful of historical timezone transitions — `Pacific/Apia` skipped `2011-12-30` entirely when it moved across the International Date Line in 2011 — the same input string validated successfully under one timezone and failed under another. `DateFormat::validate()` now passes an explicit UTC `\DateTimeZone` as the fallback timezone to `createFromFormat()`, making the result independent of server configuration; a format that embeds its own timezone info (e.g. `P` or `e`) is unaffected, since `createFromFormat()` only falls back to the passed timezone when the format supplies none.
- **`MimeTypeString` no longer rejects syntactically valid RFC 6838 names ending in punctuation.** Its pattern required the last character of both the type and subtype to be alphanumeric, but RFC 6838's grammar restricts only the *first* character (`restricted-name-first`) — every character after it, including the last, may be any `restricted-name-chars` member. Values like `application/vnd.example.` or `text/plain-` are syntactically legal per the RFC and are now accepted; the length cap (127 characters per side) is unchanged.

### Documentation

- **Corrected several factually wrong claims caught by re-running the documented examples.** `docs/nullable-and-helpers.md`'s `\Stringable` row said bools render via `strval()` (giving `"1"`/`""`) and that datetimes JSON-encode in `__toString()`; bools actually render as the literal words `'true'`/`'false'`, and datetimes pass the value through verbatim (no surrounding quotes — that's `jsonSerialize()`'s job). `docs/built-in-types.md` said `(string) new TrueValue(true)` is `"1"`; it is `"true"`. Both are fixed at every place they were echoed.
- **`docs/defining-types.md`'s two custom-constraint examples (`Palindrome`, `Luhn`) now use `StrongType\Util\ShortClassName::of()`** instead of the inline `substr($className, strrpos($className, '\\') + 1)` the project's own conventions forbid (it drops the first character for a class with no namespace) — including the `use` statement each example needs to actually run.
- **`CLAUDE.md`'s `Arrays/` line now says 15 concrete types**, matching the count since the array-hierarchy `readonly` change (`ArrayType` + 15 subclasses = 16 files).
- **Documented four previously-implicit behaviors, each correct as-is:** `tryFrom()` only swallows validation failures into `null` — a misconfigured constraint still throws `ConstraintConfigurationException` from `tryFrom()`, same as `new` ([docs/nullable-and-helpers.md](docs/nullable-and-helpers.md)); `FutureTimestamp`/`PastTimestamp`/`InFuture`/`InPast` check `time()` once at construction and do not track the wall clock afterward ([docs/semantics.md](docs/semantics.md#clock-relative-validation)); `AssociativeArray` can never be empty because its `#[Nonempty]` fires before `#[IsAssociative]` gets a chance ([docs/built-in-types.md](docs/built-in-types.md)); `Rfc3339`/`Rfc3339DateTimeString` accept year `0000` while `DateString` rejects it via `checkdate()`'s Gregorian floor — each honors a different contract by design ([docs/built-in-types.md](docs/built-in-types.md), [docs/constraint-attributes.md](docs/constraint-attributes.md)).
- **Documented, louder, that a `BoolType` subtype narrowing its constructor to a `true`/`false` literal (the `TrueValue`/`FalseValue` pattern) must override `tryFrom()` itself** or the inherited `tryFrom()` leaks an uncaught `\TypeError` for the wrong literal, instead of returning `null` ([docs/architecture.md](docs/architecture.md)).
